# პროექტის მიზანი
მოცემული პროქტის მიზანი იყო Walmart-ის სხვადასხვა რეგიონში მდებარე 45 მაღაზიის გაყიდვების პროგნოზირება. პროექტზე მუშაობისას დავტესტეთ მეთოდები: XGBoost, LightGBM, Prophet, TFT, N_beats, DLinear. PatchTST. გადმოგვეცემოდა ფაილები : train.csv მთავარი სატრენინგო ფაილი 5 სვეტით : Store, Dept, Date, Weekly_Sales (target), isHoliday. test.csv სატესტო ფაილი. იგივე რაც train.csv Weekly_Sales გარეშე. features.csv - დამატებითი მონაცემებისთვის, როგორიცაა ტემპერატურა, საწვავის ფასი, ფასდაკლების კვირეული, უმუშევრობისა და სამომხმარებლო ფასების ინდექსი. ასევე გადმოცემული გვქონდა 4 კონკრეტული დღესასწაულის თარიღები: Super Bowl, Labor Day, მადლიერების დღე და შობა.

# Feature Engineering 
Feature Engineering ს რაც შეეხება, დავამატეთ ერთი Lag სვეტი sales_lag_52 ვინაიდან ტესტ სეტი წელიწადზე მოკლეა. ასევე დავამატეთ წრიული კალენდარული სვეტებისთვის sin/cos feature ები: month_sin, month_cos, dow_sin, dow_cos (Day of week), week_sin, week_cos, month_sin, month_cos. Date სვეტიდან ამოვიღეთ წელი და ეგეც დავამატეთ feature ებში. 
რაც შეეხება კატეგორიული ცვლადების რიცხვითში გადაყვანას, isHoliday გადავიყვანეთ მარტივად 0-1 ში. ხოლო Type თვის გავაკეთეთ target_encoding და გადავიყვანეთ {'A': 20, 'B': 12, 'C': 9.5} მაპინგით.
იმ Store-Dept წყვილებისთვის რომელიც ტრეინში არ იყო sales_lag_52 ად ვცადეთ აღება საშუალო sales_lag_52ს იგივე Store და Type თვი#ს, თუმცა კარგი შედეგები არ მივიღეთ ამიტომაც ამოვიღეთ (კომიტებში იქნება)

# XGBoost LightGBM
XGBoost LightGBM არქიტექტურებისთვის ვიყენებდით ყველა იმ feature ს რომელზეც გვქონდა საუბარი. ასევე ვცადეთ sales_lag_52 ის გარეშეც თუმცა ოდნავ უარესი შედეგები მოჰყვა. ვცადეთ Store Dept ის გარეშეც (ვინაიდან ზოგი დეპარტამენტი ტესტშეტშია თუმცა ტრეინ სეტში არაა), თუმცა ბევრად უარესი შედეგები მოჰყვა. 

# Prophet
Prophet რაღაც მხრივ პრობლემური არქიტექტურა იყო, ვინაიდან per-series არის. თითოეული Store-Dept წყვილისთვის ვცადეთ მოდელის დაგენერირება და შენახვა. ასევე ვცადეთ მაღაზიების დაჯგუფება სხვადასხვა მნიშვნეკოვანი feature ების მიხედვით. მაგალითად, sales_lag_52ის მიხედვით გავაკეთეტ sales_bin ები და დავაჯგუდეთ მასთან და type თან (ვინაიდან Type იც მნიშვნელოვანი featureია). ასევე ვცადეთ დაჯგუდება Type ით და Size_binებით, თUმცა მანაც არცთუ კარგი შედეგი დადო

# TFT (Temporal Fusion Transformer)
TFT სხვაა მოდელებისგან განსხვავებით მონაცემებს ყოფს და ამუშავებს განსხვავებული პრინციპით:
უცვლელი მონაცემები - მაღაზიის/დეპარტამენტის ID მაგალითად

მონაცემები, რომლების მომავლის value-ებიც ცნობილია - არდადეგები მაგალითად, კალენდარში წინასწარ რაცაა მონიშნული

მონაცემები, რომლების მხოლოდ წარსულის value-ებია ცნობილი - Weekly_Sales მაგალითად

"სამიზნე" - რის წინასწარმეტყველებასაც ცდილობს მოდელი

# DLinear
ყველაზე მარტივი მოდელი, რომელმაც ჩვენს შემთხვევაში ყველაზე კარგი შედეგი დადო(საბოლოო WMAE კეგლზე - 2876.477). მოდელი იყენებს მხოლოდ წრფივ შრეებს პროგნოზისთვის. მიღებული მონაცემები იყოფა ტრენდულ და სეზონურ კომპონენტებად. ტრენდული კომპონენტი პასუხისმგებელია სტაბილურ და ნაკლებად ცვლილებად sale-ებზე, სეზონური კომპონენტი კი უჩვეულო spike-ებს აფიქსირებს(არდადეგები). ორივე კომპონენტისთვის თითო წრფივი შრე გამოიყენება და შემდეგ მათი შედეგები უბრალოდ ჯამდება.
მონაცემების მოსამზადებლად გვაქვს Sliding Window მიდგომა, რომლის ფარგლებშიც მოდელი ფიქსირებულად უყურებს წარსულის 52 კვირიან ფანჯარას(LOOKBACK = 52) და მომავლის 39 კვირის პროგნოზს ახდენს(HORIZON = 39).
ასევე ვიყენებთ ნორმალიზებას, რომ გავითვალისწინოთ მაღაზიებს შორის ზომის განსხვავებები. დიდ მაღაზიებს უფრო დიდი Weekly_Sales აქვთ და მაგან არ უნდა დააბნიოს მოდელი. ამიტომ თითოეული მაღაზიისთვის weekly_sales იყოფა ფანჯრის საშუალოზე.
